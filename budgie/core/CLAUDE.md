# budgie/core — module notes

Moved from the root `CLAUDE.md`, which keeps the two architecture rules (no UI imports under `core/`; nothing heavy at module scope in `budgie/budgie.py`).

- `budgie/core/csvio.py` — the stdlib-`csv` reading layer every loader uses. **pandas is no longer a dependency**: inputs are small flat human-edited CSVs that were immediately iterated into frozen dataclasses, and pandas cost ~0.5s of import before anything printed. `read_rows(path, required)` returns a `Table` (a list of `{column: value}` dicts that also carries `.columns`, so a loader picking its shape from the header works on a header-only file). `as_float`/`as_required_float`/`as_int`/`as_str`/`as_date` convert with errors that name the column; `parse_date` takes ISO plus the usual spreadsheet exports. **Each row is a `Row` (a dict) carrying `.where` (`plan.csv line 3`, the physical line, header = 1) and `.line`**, and the helpers raise through `row_error(row, msg)`, which prefixes it — so a loader gets file+line by converting through the helpers and raising its own checks with `row_error`. Only one layer prefixes: never wrap a loader body in a try/except that adds the location again. Loaders refuse absurd values the same way (people.csv: negative rate, blank/duplicate name compared casefolded, `util_*` outside 0..1, out-of-order low/mode/high, empty file; plan.csv: blank name, `fte` outside 0..1; allocations.csv: `fte` outside 0..1; costs.csv: `CostItem`'s own checks re-raised with the line; weekly.csv: unknown week, and a cumulative decrease, which names the line of the lower reading).
- `budgie/core/calendar.py` — productive-hours calculation. `productive_hours(span, pto_days)` = 40 hrs/week × 52 (=2080 gross) minus US federal holidays (via the `holidays` package, anchored to a YearSpan — every calendar year the span touches, so weekend-observed shifts are correct and a fiscal year counts both years' holidays), optionally minus PTO to reach "available hours". ~1992 productive hrs/yr. **`YearSpan` / `year_span(year, year_start)`** is the money year: `01-01` is the calendar year, `10-01` the federal fiscal year (FY27 = 2026-10-01..2027-09-30). Every January 1 / December 31 in core reads from it.
  - **PTO is pro-rated by FTE**, and this is the most-asked question about the model: the ceiling is computed full-time and *then* multiplied by FTE, so a 0.25 FTE person surrenders a quarter of their PTO to the project. The rule lives in one place as `PTO_RULE` (with `explain_pto()` for a worked example) so the CLI, TUI and README can't drift from it.
  - `ProductiveHours.available_for(pto_days)` and `resolve_ceiling(ceiling, pto_days)` support a per-person `pto_days` column. `resolve_ceiling` **raises** if given a per-person figure alongside a bare float ceiling — the float has already had PTO subtracted and can't be un-subtracted, so silently double-counting would be the alternative. Loaders therefore want the `ProductiveHours` object, not `.available_hours`.
- `budgie/core/workspace.py` — the project. **Projects live together under a `budget/` container** (`PROJECTS_DIR`): `budget/fy26/budgie.yaml`, `budget/fy27/budgie.yaml`. The container is not itself a project — but `budget/budgie.yaml` (the shape earlier versions wrote) still is, and a project directly below cwd is still found, so pre-container layouts keep working. `find_workspace(start, project)` walks up from cwd looking for `budgie.yaml`, then falls back to the **single** project below — because `init` scaffolds into a subfolder, so the next command a user runs is one level above it. Two candidates below means no guess: picking the wrong budget silently is worse than reporting no project. A config *above* still wins over one below, but an explicit `project=` name beats both — `--project fy27` typed from inside `fy26` has to mean `fy27` or the flag does nothing where it's most likely to be used. (cached; call `forget_workspaces()` after writing one or in tests).
  - `available_projects(start)` → `list[Project]` is what makes the ambiguous case actionable: the engine declines to choose, and the front-end lists the candidates instead of saying "no project found". `_projects_below` looks both directly below a directory and inside its `budget/`, de-duplicated by root and sorted by name.
  - `INPUTS` is the single registry of every known input: config key → (default filename, description, which commands consume it), and it drives `budgie status`, the TUI Inputs tab, and the generated project README. `Workspace.resolve(key)` returns a path only if the file exists, so declaring a project never makes a command demand a file you haven't written.
- `budgie/core/guide.py` — the walkthrough content as data: `COMMAND_GROUPS` (the grouped help listing), `PHASES` (build a budget in order), `TOPICS` (per-input-file columns, example, rules). UI-free; filenames and consumers are read back out of `workspace.INPUTS` so there is one registry, not two. Two tests assert `COMMAND_GROUPS` and `cli.commands` are the same set in both directions, so a new or renamed command can't go missing from the landing screen or leave a dead entry on it.
  - `_rules(...)` / `_cols(...)` are calls, not tuple literals, purely because ruff's ISC004 flags implicit string concatenation inside a collection literal and these entries have to wrap.
- `budgie/core/scaffold.py` — project lifecycle: what `budgie init` writes, and `delete_project()`, the one irreversible thing Budgie does. Deletion **refuses rather than guesses**: the target must contain a `budgie.yaml` (so a mistyped path errors instead of eating a home directory), must not be a symlink, and must not contain the cwd (deleting the ground you're standing on leaves every later command resolving against a path that's gone). Confirmation is the caller's job — by the time it runs, the files are going. Both front-ends make you confirm *specifically*: the CLI has you type the project's name back (a reflexive `y` is too cheap for something with no undo, and `--yes` is the scriptable path), the TUI arms on the first `d` and deletes on the second. Templates are strings here rather than package data so they can't drift from the loaders. **The generated CSVs carry no comment lines** — a `#` row is a malformed record to a CSV reader — so all explanation lives in `budgie.yaml` and the generated `README.md`, and the example rows are real loadable data. Template dates come from the span (`start`, `third_month_15`, `fifth_month`), so a calendar project's files are unchanged and a fiscal one's start on its first day.
- **One model (budgie-3oj): plan.csv sets the hours.** `project.people_on_plan(people, plan, span, pto, pto_by_name)` is the only place a person's hours come from when a project has a plan: likely = `plan.allocated_hours`, low/high = likely × `Person.spread`. `load_snapshot`, `Snapshot.what_if`/`with_plan`, and the CLI's `forecast`/`monthly` (`_on_plan`) all call it, so a plan edit moves cost everywhere. Rules, each a sentence in `Snapshot.warnings` (shown, never only logged): a rate with no plan rows is 0 hours; a plan name with no rate isn't costed (with a case-slip hint); no plan rows is 0 hours even when allocations.csv gives an `fte` (decided from the mocks; this also means a chained `with_plan` can't resurrect a removed person, budgie-y5r); util_mode 0 means no spread; people.csv `pto_days` beats allocations.csv's. `loader.load_people` records `Person.spread` for every form and reads the new **plain form** `name,hourly_cost[,under,over]` (percent, hours 0 until a plan applies). Only the project's own plan applies: the CLI skips it for the bundled sample and for an explicit `--people` file. allocations.csv `fte`/`hours_spent` are optional (a present column must still be filled in).
- `budgie/core/allocation.py` — FTE tracking (separate concern from forecasting). `Allocation` converts an FTE fraction × the year's available hours into allocated hours, subtracts `hours_spent` → `hours_remaining`, and flags `is_over_budget`. `load_allocations(csv, available_hours, plan=None)` reads `name[,fte,hours_spent,email,pto_days]`.
  - **With a `plan`, plan.csv is the source of truth for allocated hours.** `fte` becomes the **year-average effective FTE** — `plan.allocated_hours(name, year, pto) / ceiling` — chosen so `allocated_hours == fte * available_hours` still holds and `Allocation` needs no new field. A row's own `pto_days` is honoured on both sides of that division. Someone the plan doesn't mention keeps their flat `fte`. Someone only in the plan is appended (plan order) with 0 spent. Both cases log a warning. A plan with a bare float ceiling **raises**, same reasoning as `resolve_ceiling`: the day-by-day walk needs the year and the PTO figure. `AllocationPlan` is imported under `TYPE_CHECKING` only, so this module doesn't pull in `holidays` via `plan.py`.
  - In the CLI, `hours` and `emails` resolve `--plan` through `_plan_for_allocations()` — `_workspace_input`, deliberately **not** `_input`. The bundled sample plan names different people than the sample allocations, so a sample fallback would invent a team.
  - `pto_overrides(csv)` → `{name: pto_days}` is how the **plan views** (`budgie plan`, the TUI Plan tab) use the same per-person PTO as `hours`. Without it the two disagree about the same plan.csv (a Bob at 0.85 FTE with 20 PTO days: 1,557 vs 1,693).
- `budgie/core/costs.py` — non-labor lines (materials/licences/travel). `CostItem` carries `amount` plus optional `low`/`high`, so uncertain costs sample triangularly into the same Monte Carlo as hours. `recurring=True` books the amount **every month from its own month through the year's last month** (`months_charged`, counted inside the item's `span`: from `max(when, span.first)` through `span.last`; **a line dated before the year is charged from the year's first month, one dated after it 0 months**, and `total == sum(monthly_totals)` for every recurring line. `load_costs(csv, span=)` sets it; a bare `CostItem` with no span keeps the legacy `when`-through-December rule), so `total` ≠ `amount` for those. `monthly_totals()` places each line in the month incurred. Costs flow in via optional `costs=` params on `forecast()`, `simulate()`, `monthly_forecast()`, and `monthly_simulation()` — all default to empty, so existing callers are unaffected.
  - **Presentation trap:** `Forecast.total_cost` is labor **+** non-labor. A per-person table's total row must use `.labor_cost`, or the rows won't sum to the total shown.
- `budgie/core/budget.py` — budgets as dated revisions rather than a scalar. `Budget.amount_on(date)` forward-fills (and returns the *original* for dates before the first revision — a budget set in May still governed that January). `original` / `latest` / `net_change` expose the drift; `monthly_amounts()` drives the stepped budget line on the fan chart. `coerce_budget()` accepts a number, a list of `{date, amount, note}`, or a CSV path, which is what keeps `budget: 720000` in existing scenario configs working. **Signals compare against `latest`, not `original`.**
- `budgie/core/plan.py` — **date-resolution** allocation planning. `load_plan()` reads `name,effective_date,fte`; each row applies from its date until the next row for that person, and 0 FTE applies before their first row. So "add member", "zero out", and "re-plan" are all just an appended row — never edit history. `allocated_hours()` walks the year **day by day** at the FTE in effect, so a mid-month start is charged from the actual day (Carol joining 2026-07-15 at 0.5 FTE → 466 h, not 996 flat or 502 month-rounded).
- `budgie/core/solve.py` — what-if solving over a plan (epic budgie-w3l). `PlanCosting` prices a plan as rate × (hours up to `as_of`, or `spent` when given, + plan hours after it) + non-labor; this is step B's one-model total, the same number the Forecast tab shows. Cost is linear in FTE, so `solve()` is closed-form: `proportional` scales the chosen cells by one factor, `even` adds one FTE to each, and cells clamped to `[0, cap]` are fixed while the rest are re-solved, with the gap still open reported rather than hidden. `read_month_sheet(path, span)` reads the grid's import sheet (`name` then the span's months **in the span's order**, so a Jan..Dec sheet on an Oct-start year is an error rather than a year-off import; blank = no edit; FTE 0..1 with csvio line errors) into the same `{(name, month): fte}` cells. `entries_for()` turns cell edits into appended plan rows, and adds a row at every older change date inside an edited month, since otherwise that older mid-month row wins from its date (same-date rows resolve by the stable sort, last appended wins). Preview and commit both use those rows. `PlanCosting.span` is the money year: `months(span)` follows `span.months`, so a cell's month is its place in the year (1 = the span's first month, October in FY27), not a calendar month number, and holidays come from every calendar year the span touches.
- `budgie/core/actuals.py` — observed spend as `(date, cumulative_hours)` tuples. `load_weekly_actuals()` reads `name,week,hours_to_date` — real timesheet exports give a **cumulative reading at an ISO week**, not a per-week series, so values are validated as non-decreasing (a decrease means someone pasted per-period values). `week_ending()` maps ISO week → its Sunday. `monthly_to_observations()` converts the monthly shape into the same form, and **stops after the last month with hours**: a trailing empty month is a month nobody has reported yet, not a reading of zero — emitting it dated the latest observation on the year's last day, which `burndown()` then took as its as-of date (0 working days left). An empty month *between* reported ones is a real reading and is kept.
- `budgie/core/eac.py` — estimate at completion. **A triangular estimate that is scaled and shifted is still triangular**, so there is no second simulator: `at_completion(people, observations, span, as_of)` returns a `Completion` whose `.people` are ordinary `Person` objects with `low/mode/high` each rewritten as `spent + x × (1 − f)`, and `forecast()`, `simulate()`, `signals.evaluate()` and the plots consume them unchanged. `f` is `plan.fraction_through(name, span, date)` when `at_completion(..., plan=)` has hours for that person (the CLI's `_with_actuals` passes the project's `plan.csv`, never the sample), else `elapsed_fraction(span, date)` — working days through the date *inclusive*, over the year's. **`f` is measured at the reading's own date; `as_of` only filters which readings count** — hours after the reading are unknown, so that stretch has to stay forecast rather than be silently treated as zero. `.readings` (name → the `(date, spent)` used) is what the CLI prints; people absent from it are returned untouched (`is` the same object). Stated assumptions: spent hours are costed at the current rate, non-labor is not adjusted. Names in the actuals that match nobody get one warning. In the CLI, `forecast` with no readings must render exactly as it did before — `_print_forecast_table(det, readings)` only changes shape when `readings` is non-empty.
- `budgie/core/project.py` — **which input wins, in one place**, for the CLI and for perch (which reads Budgie projects from outside): `readings_files` (a named file beats the project's copies, and the project's are consulted **only when neither `--actuals` nor `--weekly` was given** — weekly outranks monthly, so resolving each flag on its own lets the project's weekly.csv silently beat an explicit `--actuals`), `load_observations` (weekly beats monthly), `spent_to_date` + `with_readings` (the latest dated reading beats `hours_spent`; `hours` applies it so it agrees with `emails`), `budget_source` (a pinned `budget:` beats budget.csv). `load_snapshot(dir)` is the whole-project read with every rule applied (`Snapshot.budget_revisions` is the loaded budget.csv `Budget` with its dated revisions, None when the budget is a pinned number or absent; `Snapshot.costs` is the loaded costs.csv lines (low/high kept; `non_labor` is their `total_cost`) so callers can pass `costs=` to `simulate`/`forecast`; `Snapshot.plan` is the project's own plan.csv `AllocationPlan`, never the bundled sample, or None); `Snapshot.what_if(budget=None, plan_entries=())` is the pure, file-free copy with a flat replacement budget (so `budget_revisions` becomes None) and extra plan entries appended, allocated hours recomputed through the plan the way `load_snapshot` does (a plan beats `fte`; people only in the new entries are added with nothing spent; an allocations-only person named in the entries is first seeded at their flat `fte` from the year's first day, so a leave date doesn't zero their whole year); perch builds from it and its `test_contract.py` names it. A new precedence rule goes here, never in `budgie.py` or a caller.
- `budgie/core/monthly.py` — the monthly time dimension. Months are weighted by **actual working days** (Mon–Fri minus federal holidays in that month), never an even 1/12, and `month_weights()` sums to 1 so monthly figures always reconcile back to the annual ones from `calendar.py`. Provides `monthly_forecast()`, `monthly_simulation()` (cumulative cost per month, `.band(p)` for fan-chart percentiles), `cumulative()`, and `load_monthly_actuals()` (tidy `name,month,hours` CSV → `{name: [12 monthly hours]}`).
  - **With `actuals=Actuals(readings, observations, plan)`** (both `monthly_*` functions; the CLI builds it from `_with_actuals`, the same helper `forecast` uses, so readings/`--as-of` resolve identically) the `people` passed in are already the EAC team. Per person, cumulative hours at a month end are `booked + (total − spent) × share`: months ending before the latest reading are *booked* (`spent_at`, public; `_spent_at` is a temporary alias for perch's current import, drop it once perch switches; linear between readings, so weekly data is interpolated, not measured), later months carry the reading and a share of the remaining hours taken from `plan.fraction_through` (fallback: `elapsed_fraction`). Anyone without a reading keeps today's working-day weights. `actuals=None` takes the old code path unchanged. Non-labor is not adjusted.
- `budgie/core/burndown.py` — `burndown(allocation, span, as_of)` → `BurndownStatus`: even-pace expectation vs actual spend (`variance`, `is_over_pace`), observed `burn_rate_per_day`, `projected_total`, and `exhaustion_date` (None if the allocation lasts the year). Accepts optional `monthly_spent` cumulative actuals; **without it we only know the endpoint**, so the chart interpolates from the origin — don't present that line as measured month-by-month data.
  - **With a `plan`, pace follows the plan.** `expected_on(day)` / `expected_by_now` = allocated hours × `plan.fraction_through(name, span, day)` (a ratio, so no PTO figure is needed); `required_pace` ends on `plan.last_planned_day`, so a plan that has ended with hours left reads as `out_of_time`. Someone the plan has no hours for keeps the even burn. The chart's pace line is drawn from `expected_on`. `plan.allocated_hours(..., through=date)` is the general helper.
  - **With observations, `burndown()` rewrites `allocation.hours_spent` to the latest reading.** A status carries one spent figure; otherwise a draft quotes the allocations.csv scalar in its table and the reading in its pace sentence.
  - `.required_pace` → `RequiredPace`: remaining hours restated as `hours_per_week` and an `fte` fraction, over the **real working days left** after `as_of` (not `weeks × 5`) — a December reading must not imply capacity that isn't there. `is_exhausted` / `is_impossible` / `out_of_time` cover the degenerate cases so callers don't divide by zero or print a 300% FTE with a straight face. This is what makes "318 hours left" actionable.
- `budgie/core/signals.py` — rules-based stoplight analysis. `evaluate(sim, budget, baseline=None)` → `SignalResult` with a `Signal` of GREEN (good, ≤10% chance over budget) / YELLOW (caution, ≤40%) / RED (bad, >40%) / BLUE (no change — only when a `baseline` sim is given and the mean moved ≤2%). The driving number is `probability_over()`, read straight off the simulated outcomes. Thresholds are keyword args, not magic numbers.
- `budgie/core/scenario.py` — `run_scenarios(config)` runs named what-if scenarios from a YAML config (`budget`, `iterations`, `seed`, `scenarios[]` each with `name/people/year/pto`) → `(list[ScenarioResult], budget)`. **The first scenario is the baseline** for both `cost_delta` and the BLUE signal. People paths resolve relative to the config file's directory. **With a `budgie.yaml` beside the config, each scenario is that project's `load_snapshot(year=, pto=)` run through `at_completion` like `budgie forecast`** (plan.csv, readings, costs), so the baseline equals `forecast`; `people`/`costs`/`year_start` that differ from the project's raise a one-line error (no `what_if` counterpart). Without a project, people.csv alone, as before.
